# Guru prompt flow: what each LLM is sent, step by step

Generated by rendering the **current code** (`agent/guru/interviewer.py`, `prompts.py`, `llm.py`, `kb.py`, `planner.py`, `scorer.py`) with LiveKit Agents 1.8.8's own message formatters (`livekit.agents.llm._provider_format.google` / `.openai`). Nothing below is shortened.

**Test values.** Job, plan and question bank: `agent/fixtures/plan.json` and `fixtures/job.json` (Northwind Analytics, Senior Backend Engineer). Candidate answers, interviewer replies and observer notes: the console run on 31 Oct 2026 16:57-17:02 in `agent/logs/guru.txt`; the consent line from `agent/out/console.json`. That run used the **old** code (prompt rebuilt with `refresh()`), so the replies are real but would not be word-for-word identical today. Anything marked **SAMPLE** has no log to copy from (no company question was asked in any logged run).

**How to read a request.** Each voice-LLM call shows the full JSON that Gemini receives. `system_instruction` is the system prompt; `contents` is the conversation; `tools` are the function declarations. A system message added mid-conversation (the current-question block, a `generate_reply(instructions=...)`) is not merged into the system prompt: LiveKit rewrites it as a `user` part wrapped in `<instructions>…</instructions>` at its position. OpenRouter (the fallback) keeps those as `system` messages in place; one turn shows its payload too.

## 2. Before the interview: Planner

- **Caller:** `planner.make_plan()`
- **Trigger:** recruiter saves the job (`uv run python -m guru.planner fixtures/job.json fixtures/kb`); OpenRouter flex tier

## 5. Known issues found while rendering this flow

**1. Every preemptive generation is now thrown away.** LiveKit starts the preemptive request from `self._agent.chat_ctx.copy()` before `on_user_turn_completed` runs (`voice/agent_activity.py`, `on_preemptive_generation`). After the hook, it reuses the preemptive reply only if `preemptive.chat_ctx.is_equivalent(temp_mutable_chat_ctx)`; the hook always adds a message, so the lengths differ and the reply is cancelled (calls `I2a`, `I3a`, …). Each turn pays for an extra LLM request and loses the latency gain preemptive generation was enabled for. `s.llm_cancelled` in `out/<session>.json` will show it.

**2. The tool reply after `advance_to_next_question` still carries the old question's block.** LiveKit builds the tool-reply request from the same turn context (`chat_ctx.items.extend(tool_messages)` then `merge(...)`), so the block from that turn stays in it: "Current question (1 of 3)… Do not ask more follow-ups: call advance_to_next_question now." sits next to the tool result "Ask this next question now…" (calls `I4c`, `I6c`). The old `refresh()` design did not have this, because `update_instructions` refreshed the system prompt before the tool reply. Risk: the model calls `advance_to_next_question` again and skips a question.
